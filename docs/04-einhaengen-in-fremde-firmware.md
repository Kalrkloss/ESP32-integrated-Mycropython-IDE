# Can a FreeRTOS task be "hooked into Annex"?

Question: Annex is based on FreeRTOS — can a task that does the
USB playback be added afterwards and hooked into Annex?

Short answer: **No.** Not because FreeRTOS is missing, but because in a fully flashed
firmware there is no place where foreign code lands. A task exists only if it was
**linked together** with the firmware. Annex has no plugin, module or
CSUB system through which native code could be loaded at runtime — the documentation knows
exclusively built-in commands (`MODULE` variants of the firmware are the author's compile-time
manifestations, not a user extension point).

## The three technically conceivable ways — and why they fail here

### 1. Loading an ELF at runtime

Something like this actually exists: `espressif/elf_loader`
(<https://components.espressif.com/components/espressif/elf_loader/>) loads ELF files
or shared objects on the ESP32/S3 at runtime and offers `dlopen`/`dlsym`/`dlclose`.
With it one could in principle start a recompiled `.so` with a FreeRTOS task.

Prerequisites that are missing here:

- The **firmware** must provide its symbols to the loader. The ELF loader works
  with `esp_elf_register_symbol(...)` of a symbol table generated by the project
  (`build/generated/.../esp_elf_example.c`). Annex is a ready-made, symbol-free
  image — it registers nothing.
- Your `.so` would have to bind against Annex' internal functions: `xTaskCreate`, the
  USB host API, the BASIC command table, the sound/I2S code. Their addresses appear
  nowhere. They would have to be obtained from the binary via disassembly/decompilation —
  exactly what the Annex license expressly prohibits.
- ABI equality: the code would have to be built with the same ESP-IDF version and the same
  `sdkconfig` options as Annex's firmware. Neither is published.

### 2. Patching the binary

Find free flash, patch a jump into an init function to a trampoline (Xtensa
assembler) that calls `xTaskCreate`. Result: at best a task runs.

What does **not** happen with it:

- No coupling to Annex. Without a hook into the command table there are no
  BASIC commands; the user cannot control playback from BASIC.
- Annex' own sound engine (`PLAY.*`, `SOUND.*`, I2S + DMA) occupies the same
  peripheral and DMA resources. Two competing audio paths are not a feature
  but a fault condition.
- Every OTA update changes all addresses → re-patch after every firmware update.
- Budget unknown: the S3 image is 2.87 MB (bootloader + partition table + app),
  free space in the app partition and in RAM cannot be determined from outside.

### 3. Second core / free OTA slot

The S3 has two cores, but a device runs **one** firmware. A free OTA slot
is not started by itself, and there is no second kernel into which one could place an
independent audio task. That is not a way.

## Conclusion

"Hooking a task into Annex" is exactly the operation that **presupposes source code**.
There are two ways to get there:

1. **The author builds it in** (way A). cicciocb has the task level, sound engine and
   command table; the USB host stack is already in the S3 build (variants with
   `HID`/`OTG`, docs: "USB HID INTERFACE (Mouse, Keyboard, Gamepad) — ESP32-S3 only").
   For him, a UAC host driver based on `espressif/usb_host_uac` is a
   manageable addition. Draft for it: [05-feature-request-cicciocb.md](05-feature-request-cicciocb.md)
2. **Own firmware** (way B). There you are the author yourself: the FreeRTOS task for
   USB playback is trivial, and the BASIC command level is cleanly put in front of it.
   This repository exists precisely for that — see [02-plan.md](02-plan.md).

## Not examined

- Whether Annex internally does have a call site for user code (nothing emerges from the
  manual and download list; without decompilation this remains an assumption).
- With which ESP-IDF version the current S3 binaries are built.
